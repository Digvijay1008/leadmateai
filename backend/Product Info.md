Uchchar — Complete Product Vision & Platform ArchitectureRead this fully before writing a single line of code. This document explains exactly what we are building, which platform does what, and how every component connects. Every technical decision must align with this vision.The Simple Way To Understand UchcharImagine Uchchar as a hotel. The hotel has many rooms. Each room belongs to a different business — Clinic A in Room 1, Coaching Center B in Room 2, Real Estate Agency C in Room 3. Every room is completely private — guests in Room 1 can never see, hear, or interact with anything in Room 2. Each room has its own phone number, its own AI receptionist with its own personality and knowledge, its own billing meter running independently.Uchchar is the hotel. We manage the infrastructure. Businesses rent rooms. Their customers call the room's phone number and talk to that room's AI receptionist. That is the entire product.Platform Responsibilities — Who Does WhatPlivo — The Phone Company
Plivo's only job is to own Indian phone numbers and route calls. When a business signs up on Uchchar, we provision them a Plivo phone number programmatically. When anyone calls that number, Plivo fires a webhook to our backend saying "hey, someone is calling number +91-XXXXXXXXXX." That's it. Plivo knows nothing about AI, nothing about tenants, nothing about billing. It just delivers the call to us.Future consideration — research LiveKit native SIP trunking as a potential replacement for Plivo to reduce per-minute costs. But Plivo first, optimization later.LiveKit — The Audio Highway
LiveKit's job is to create a real-time audio room and manage the voice session. When Plivo webhook fires, our backend tells LiveKit to create a room and dispatch an agent to that room. LiveKit handles all the WebRTC complexity, audio encoding, network optimization, and agent worker management. LiveKit also tracks session duration natively which we use as our billing backup.Think of LiveKit as the telephone exchange inside our hotel. It creates the call connection and keeps it stable.Python Agent — The Brain
The Python agent is our AI receptionist. It lives inside LiveKit's audio room. Its job is to listen to the caller, understand what they're saying, think of the right response, and speak back naturally. It does this using three sub-components — STT converts caller's voice to text, LLM thinks of the response, TTS converts response back to voice.Critically — the Python agent is completely stateless. It reads its instructions from the session manifest at the start of each call and forgets everything when the call ends. All persistent data lives in the database, never in the agent.Node.js Backend — The Manager
The backend is the brain of the entire operation. It handles everything that isn't real-time audio. Business signup and authentication, phone number provisioning via Plivo API, session manifest creation per call, billing wallet management, call logging, dashboard API, webhook processing from Plivo and LiveKit. Every decision about which tenant owns which call, how much to charge, what configuration to use — the backend makes these decisions.Supabase PostgreSQL — The Memory
The database remembers everything. Every tenant, every agent configuration, every knowledge base chunk, every call record, every wallet transaction. Every single database query must include tenant_id. No exceptions. The database is the single source of truth for the entire system.Frontend Dashboard — The Control Panel
This is what the business owner sees and uses. They log in, configure their agent, upload their knowledge base, manage their phone numbers, top up their wallet, and view their call history. This is the product the customer pays for. Everything else is invisible infrastructure.The Complete Call Flow — Step By StepThis is the most important thing to understand. Every line of code must serve this flow.Step 1 — Customer calls the clinic's Plivo number.Step 2 — Plivo fires webhook to our Node.js backend with the incoming phone number.Step 3 — Backend looks up which tenant owns this phone number in the database.Step 4 — Backend checks tenant's wallet balance. If insufficient funds, backend instructs Plivo to play a "service temporarily unavailable" message and ends the call. Customer is never connected to an underfunded agent.Step 5 — Backend creates a wallet HOLD for the maximum possible call cost to reserve funds.Step 6 — Backend creates a Session Manifest — a JSON object containing everything the agent needs to know about this specific call. This includes tenant_id, tenant business name, system prompt, STT provider and model, LLM provider and model, TTS provider and voice, knowledge base ID, billing session ID, and backend auth token scoped to this session only.Step 7 — Backend creates a LiveKit room, attaches the Session Manifest as room metadata, and dispatches an agent worker to the room.Step 8 — Python agent worker receives the job, reads the Session Manifest from room metadata, configures itself entirely based on that manifest — which STT provider, which LLM, which TTS voice, which system prompt, which knowledge base to query. Agent is now Clinic A's receptionist, not a generic AI.Step 9 — Plivo connects the caller's audio to the LiveKit room via SIP bridge.Step 10 — Conversation happens. Caller speaks. Deepgram STT transcribes. Groq LLM thinks using Clinic A's system prompt and knowledge base context. Deepgram TTS speaks the response. This loop continues until call ends.Step 11 — Call ends. Agent sends session end report to backend with exact duration. LiveKit webhook also fires with session duration as backup. Backend reconciles both, charges the lower duration to protect customer, settles the wallet hold into an actual charge, logs the full call record with transcript.Step 12 — Clinic A's dashboard shows the call — duration, transcript, cost, caller number.This flow must work perfectly and atomically. Every step must either complete successfully or fail gracefully with proper cleanup.The Dashboard — What Business Owners NeedThis is your product. Build it with this exact feature set for MVP and nothing more.Agent Configuration Page
Business owner gives their agent a name — "Priya" for a clinic, "Rahul" for a coaching center. They write or we help them generate a system prompt — "You are Priya, receptionist at Sharma Clinic. The clinic is open Monday to Saturday 9am to 7pm. Doctors available are Dr. Sharma (General Physician) and Dr. Patel (Pediatrician). Your job is to book appointments, answer questions about the clinic, and take messages." They select their preferred STT provider and model, TTS provider and voice, LLM model. They can preview their agent's voice before going live.STT / TTS Provider Selection — This Is Critical for Future
The dashboard must show a dropdown for STT provider — currently Deepgram Nova-3 for English. In future Sarvam AI for Hindi, Whisper for multilingual. Another dropdown for TTS provider — currently Deepgram Aura-2 for English. In future Sarvam AI for Hindi, ElevenLabs for premium English voices. The agent pipeline must be built so swapping providers is a configuration change, not a code change. The manifest tells the agent which provider to use. The agent has adapters for each provider. Adding a new provider means adding a new adapter and a new dropdown option — nothing else changes.Knowledge Base Page
Business owner uploads their information. This can be a PDF of their brochure, a text file of FAQs, a list of services and prices, doctor schedules, anything. We chunk it, embed it, store it in a vector store tagged with their tenant_id. When their agent is on a call and needs to answer a question, it queries only their knowledge base chunks — never another tenant's data. The business owner can add, edit, or delete knowledge base entries from the dashboard. They can see which documents are uploaded and when they were last updated.Phone Numbers Page
Shows all phone numbers assigned to this tenant. Each number shows which agent is assigned to it, call volume this month, status active or inactive. Business owner can buy additional numbers from this page. They can assign different agents to different numbers — a clinic with two branches can have two numbers each with slightly different configurations.Call History Page
Every call listed with date, time, duration, cost, caller number (masked for privacy), and call outcome. Each call is expandable to show the full transcript. Business owner can search and filter calls. They can see at a glance — how many calls today, how many appointments booked, how many calls missed because of low balance.Wallet Page
Current balance prominently displayed. Top up via Razorpay. Full transaction history — top ups and call charges. Low balance warning when below a configurable threshold. Auto top-up option where we charge their card automatically when balance drops below threshold.Session Isolation — The Most Important Technical RequirementEvery call that is happening right now — whether it is 1 call or 500 simultaneous calls — must be completely isolated in its own context bubble. This means the following things must be absolutely guaranteed.The agent handling Call A has no access to any data from Call B. They run in separate async coroutines with no shared mutable state between them.The LLM context window for Call A contains only Call A's conversation history plus Call A's tenant system prompt plus Call A's knowledge base results. Nothing from Call B ever enters Call A's context window.If Call A's agent crashes, Call B continues without any interruption or awareness that Call A crashed.The wallet deduction for Call A touches only Call A's tenant wallet. The wallet deduction for Call B touches only Call B's tenant wallet. Database transactions must use row-level locking to prevent race conditions when multiple calls from the same tenant end simultaneously.The transcript stored for Call A contains only Call A's conversation. Call B's transcript is completely separate.This isolation is not a nice-to-have. It is the foundational promise of the product. A clinic whose patients' conversations bleed into another clinic's records is a product we cannot sell and a legal liability we cannot afford.STT and TTS — Build For Swappability From Day OneRight now we use Deepgram for both STT and TTS. In the near future we will add Sarvam AI for Hindi. After that potentially ElevenLabs for premium voices, Whisper for multilingual, Azure Cognitive Services for enterprise customers. We do not know exactly what providers we will add but we know we will add more.Because of this, the STT and TTS layers must be built as adapters behind a common interface. In Python this means an abstract base class or protocol.The STT adapter interface must have one method — transcribe stream — that accepts an audio stream and returns a text stream. How it does that internally — whether it calls Deepgram, Sarvam, or Whisper — is the adapter's private concern. The agent calls the interface, not the provider directly.The TTS adapter interface must have one method — synthesize — that accepts a text string and returns an audio stream. Again the agent calls the interface.When the manifest says STT provider is Deepgram and model is Nova-3, the agent instantiates the Deepgram STT adapter. When a future manifest says STT provider is Sarvam and language is Hindi, the agent instantiates the Sarvam STT adapter. The rest of the pipeline is identical. Adding Sarvam means writing one new adapter class and registering it — nothing else in the codebase changes.This is not over-engineering. This is the minimum viable architecture for a product that will have multiple providers within the next 90 days.Multi-Worker Scaling — Configure It NowThe agent must be configured for multi-worker mode immediately. Not when we get to 50 customers. Now. The configuration must be environment-variable driven.In production WorkerOptions num_idle_processes must read from an environment variable AGENT_WORKER_COUNT defaulting to 5. On Railway we can change this variable and redeploy to scale without any code changes.Each worker is a completely independent process with no shared memory with other workers. Workers communicate only through the database and through LiveKit's job dispatch system. This is the correct architecture for horizontal scaling.
